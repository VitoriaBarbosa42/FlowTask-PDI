Epic 5 — Infraestrutura como Código (Terraform & LocalStack AWS)

Especificação formal dos requisitos funcionais, não-funcionais, critérios de aceite, estratégia de persistência híbrida e governança financeira (FinOps) para o provisionamento declarativo do middleware local e simulação de serviços AWS com Terraform.

1. Objetivo de Negócio (O Por Que)

Dimensão 1/5 SDD

"Substituir scripts manuais e o docker-compose estático por uma infraestrutura modular, versionada, idempotente e reproduzível com Terraform, permitindo subir todo o middleware de desenvolvimento local em menos de 45 segundos e simular recursos corporativos de nuvem (AWS S3, SQS, Secrets Manager) via LocalStack com custo financeiro zero."

Dores Resolvidas

Elimina o clássico "na minha máquina funciona", configurações discrepantes entre desenvolvedores e a necessidade de rodar comandos manuais complexos de Docker.

Paridade com Produção

O backend utiliza os mesmos SDKs oficiais da AWS (Spring Cloud AWS, AWS SDK Java/Go), operando de forma idêntica em desenvolvimento local e na nuvem de produção.

Eficiência & FinOps

Economia de mais de $570/mês em infraestrutura de nuvem por desenvolvedor, permitindo experimentação ilimitada sem faturas reais.

2. Delimitação de Escopo (Fronteiras Estritas)

Dimensão 2/5 SDD
✅ In-Scope (Compromisso deste Ciclo)
  • • Módulos HCL Locais: PostgreSQL 15, pgAdmin 4, MongoDB 7.0, Mongo Express, Redis 7, Apache Kafka KRaft e Keycloak 24+.
  • • Módulo LocalStack AWS: S3 Bucket (flowtask-attachments), SQS Queue (flowtask-deadletter-queue) e Secrets Manager (flowtask/app-secrets).
  • • Persistência Híbrida: Mapeamento por Bind Mounts em .docker/data/ para retenção de dados após terraform destroy, com variável de limpeza forçada (clear_data_on_destroy).
  • • Isolamento de Rede: Criação de rede bridge privada (flowtask-network) com comunicação via DNS interno dos containers.
  • • Relatório FinOps Integrado: Matriz comparativa de custos de desenvolvimento local vs nuvem pública real com boas práticas de governança.
🚫 Out-of-Scope (Fora do Ciclo / Futuro)
  • • Deploy em Nuvem Pública Real: Não haverá provisionamento em contas reais pagas da AWS, Azure ou Google Cloud.
  • • Clusters Kubernetes: Não faremos provisionamento de clusters EKS, GKE ou Helm charts nesta sprint.
  • • Build e Deploy dos Apps Java/Go: O Terraform cuidará apenas do middleware/bancos; a compilação e teste dos microsserviços pertence à pipeline de CI/CD (Epic 6).
  • • Certificados TLS/HTTPS Corporativos: Ambientes locais operarão em HTTP com portas expostas em localhost sem certificados emitidos por CA pública.

3. Requisitos Funcionais (RF — 1 por Linha)

Dimensão 3/5 SDD

📦 História 5.1 — Core Middleware & Bancos de Dados

RF-01: O módulo Terraform de PostgreSQL deve instanciar um container PostgreSQL 15 na porta 5432 com banco 'flowtask' e credenciais parametrizáveis.
RF-02: O módulo Terraform de pgAdmin deve instanciar interface web na porta 5050 pré-configurada para comunicação com o PostgreSQL.
RF-03: O módulo Terraform de MongoDB deve instanciar um container MongoDB 7.0 na porta 27017 com banco 'pdi' e credenciais de acesso.
RF-04: O módulo Terraform de Mongo Express deve instanciar interface visual web na porta 8081 conectada automaticamente ao MongoDB.
RF-05: O módulo Terraform de Redis deve instanciar um container Redis 7 na porta 6379 com cache em memória e suporte a snapshot AOF.
RF-06: O módulo Terraform de Kafka deve instanciar um broker Apache Kafka em modo KRaft (sem ZooKeeper) expondo a porta 9092 para a rede do host e 29092 para a rede interna.
RF-07: O módulo Terraform de Keycloak deve instanciar servidor IAM na porta 8080 importando automaticamente o realm 'flowtask-realm.json' na inicialização.

☁️ História 5.2 — Simulação Cloud AWS com LocalStack

RF-08: O módulo LocalStack deve inicializar container emulador na porta 4566 expondo APIs para S3, SQS e Secrets Manager.
RF-09: O Terraform deve provisionar o S3 Bucket 'flowtask-attachments' configurado com versionamento ativado para armazenar relatórios e anexos.
RF-10: O Terraform deve provisionar a fila SQS 'flowtask-deadletter-queue' com período de retenção de 14 dias para eventos com falha.
RF-11: O Terraform deve provisionar o segredo 'flowtask/app-secrets' no Secrets Manager contendo chaves JWT, credenciais de banco e tokens.

⚙️ Infraestrutura, Rede & Persistência

RF-12: Todos os containers devem ser conectados à rede bridge dedicada 'flowtask-network' criada declarativamente pelo Terraform.
RF-13: A persistência dos bancos deve utilizar Bind Mounts na pasta '.docker/data/' preservando dados mesmo após 'terraform destroy' quando a flag 'clear_data_on_destroy' for false.
RF-14: O arquivo 'variables.tf' deve parametrizar portas, senhas padrões, nomes de banco e flags de ambiente com documentação e defaults seguros.
RF-15: O arquivo 'outputs.tf' deve exibir no terminal as URLs de conexão JDBC, strings de conexão Mongo/Redis, bootstrap-servers do Kafka e endpoints do LocalStack.

4. Requisitos Não-Funcionais (RNF — Métricas Numéricas)

Dimensão 4/5 SDD
RNF-01: Idempotência Estrita 0 Alterações

A execução subsequente de terraform plan após um apply bem-sucedido deve retornar rigorosamente "0 to add, 0 to change, 0 to destroy" sem flutuação de estado (drift).

RNF-02: Tempo de Convergência < 45 segundos

O tempo de execução do comando terraform apply -auto-approve em ambiente com imagens previamente baixadas deve ser menor que 45 segundos até a prontidão de todos os serviços.

RNF-03: Desligamento Limpo < 20 segundos

A destruição total da infraestrutura via terraform destroy -auto-approve deve ocorrer em menos de 20 segundos, removendo 100% dos containers e redes sem deixar processos órfãos.

RNF-04: Teto de Consumo de RAM < 2.5 GB RAM

O consumo combinado de memória RAM de todos os 8 containers de infraestrutura em estado ocioso (idle) não deve ultrapassar 2.500 MB na máquina do desenvolvedor.

RNF-05: Isolamento & Segurança de Rede DNS Bridge

A comunicação entre microsserviços deve operar via DNS interno da rede Docker (postgres:5432, kafka:29092), isolando o tráfego da rede pública do host.

RNF-06: Modularidade HCL 100% Encapsulado

Cada serviço deve residir em sua própria subpasta dentro de modules/, possuindo obrigatoriamente main.tf, variables.tf e outputs.tf.

5. Critérios de Aceite Verificáveis (Definition of Done)

Dimensão 5/5 SDD

Bateria de testes determinísticos de caixa-preta para validar se a entrega atende a 100% dos requisitos especificados:

terraform init / validate

O comando terraform init e terraform validate devem baixar com sucesso os providers kreuzwerker/docker e hashicorp/aws sem erros de sintaxe.

terraform apply

Após terraform apply -auto-approve, o comando docker ps deve listar todos os 8 containers com status Up (postgres, pgadmin, mongo, mongo-express, redis, kafka, keycloak, localstack).

HTTP & TCP Probes

Acessar com sucesso http://localhost:5050 (pgAdmin), http://localhost:8081 (Mongo Express) e http://localhost:8080 (Keycloak Realm FlowTask).

AWS CLI Local

Comando aws --endpoint-url=http://localhost:4566 s3 ls lista flowtask-attachments, e aws --endpoint-url=http://localhost:4566 sqs list-queues lista a fila flowtask-deadletter-queue.

Data Retain Test

Inserir uma linha na tabela de teste do PostgreSQL, executar terraform destroy, depois executar terraform apply e verificar que a linha inserida continua presente no banco de dados.

Zero Drift

Executar terraform plan imediatamente após apply e obter a mensagem: "No changes. Your infrastructure matches the configuration."

Pilares & Práticas de Governança FinOps Aplicadas

1. Shift-Left Cost Optimization

Testar pipelines, mensageria e upload de arquivos contra o LocalStack local antes de qualquer commit em cloud real impede faturamentos desnecessários e loops de retry que consom cotas de API.

2. Estratégia de Tagging Obrigatório

O Terraform padroniza tags em todos os recursos (Environment, Project=FlowTask, CostCenter=PDI-Eng, ManagedBy=Terraform), viabilizando alocação de custos transparente e auditoria.

3. Rightsizing & Ambientes Efêmeros

Dimensionamento mínimo de memória nos containers locais, e política de desligamento rápido (terraform destroy) que evita desperdício de recursos ociosos na máquina host.

4. S3 Lifecycle & SQS Retention Policies

Definição declarativa de expiração de objetos temporários no S3 após 30 dias e expiração de mensagens mortas na DLQ após 14 dias, evitando acúmulo de dados desnecessários.
