1. Resumo da Abordagem Técnica (O Como)

Design & Estrutura

A arquitetura de infraestrutura adotará um padrão **100% modularizado em HCL (HashiCorp Configuration Language)**, isolando a responsabilidade de cada container e serviço em subdiretórios encapsulados dentro de infra/terraform/modules/.

Módulos Docker Locais

PostgreSQL 15, pgAdmin 4, MongoDB 7, Mongo Express, Redis 7, Kafka KRaft e Keycloak 24+ instanciados via provider kreuzwerker/docker, compartilhando a rede bridge flowtask-network.

Módulo LocalStack AWS

Container LocalStack emulando a porta 4566, gerenciado em conjunto com o provider hashicorp/aws apontando para http://localhost:4566 para provisionar S3, SQS e Secrets Manager.

4. Matriz de Decisões de Design & Trade-offs (Mini-ADRs)

ADR Suite
ADR-01 Terraform com Docker Provider vs Docker Compose Puro Aprovado
Alternativa Descartada

Manter apenas o docker-compose.yaml tradicional.

Justificativa Técnica / Por Que

O Terraform introduz gerenciamento de estado (statefile), idempotência verificável, modularização estrita e habilita o provisionamento dos recursos de nuvem no LocalStack com o mesmo fluxo de trabalho declarativo.

ADR-02 Apache Kafka em Modo KRaft vs Kafka com ZooKeeper Aprovado
Alternativa Descartada

Subir 2 containers separados: 1 ZooKeeper + 1 Kafka Broker.

Justificativa Técnica / Por Que

O modo KRaft (Kafka Raft Metadata) é o padrão moderno oficial a partir do Kafka 3.x, eliminando a dependência do ZooKeeper, reduzindo o consumo de memória em ~400MB e diminuindo o tempo de boot em 50%.

ADR-03 Persistência Híbrida com Bind Mounts vs Docker Named Volumes Aprovado
Alternativa Descartada

Usar apenas docker_volume anônimos gerenciados pelo daemon do Docker.

Justificativa Técnica / Por Que

Bind Mounts em pasta física (.docker/data/) garantem que dados de desenvolvimento e testes persistam intactos após um terraform destroy, ao mesmo tempo em que a flag clear_data_on_destroy permite reiniciar o banco zerado quando necessário.

5. Análise de Riscos & Estratégia de Mitigação

Risk Assessment
Risco 1: Conflito de Portas no Host

Impacto: Se o desenvolvedor já tiver instâncias locais de Postgres (5432) ou Redis (6379), o terraform apply falhará ao tentar bindar a porta.

Mitigação: Todas as portas externas são parametrizadas no variables.tf (ex: postgres_port = 5432), permitindo override simples via terraform.tfvars.

Risco 2: Inicialização Assíncrona do Keycloak

Impacto: O Keycloak pode falhar na inicialização se o PostgreSQL ainda estiver em processo de boot criando o schema flowtask_keycloak.

Mitigação: Declaração explícita de depends_on = [module.postgres] no HCL e configuração de auto-retry no JDBC do Keycloak.
