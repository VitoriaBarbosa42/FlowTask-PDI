Como provisionar declarativamente uma malha completa de comunicação assíncrona orientada a eventos, autenticação corporativa centralizada (OAuth2/OIDC) e recursos simulados de nuvem AWS (S3, SQS e Secrets Manager) com custo zero usando Terraform.

1. Por Que Isso Importa? (Contexto & Problema Real)

Dimensão Arquitetural
Desacoplamento Assíncrono

Em sistemas de alta escala, quando o Kanban conclui uma tarefa, ele não deve fazer chamadas síncronas HTTP bloqueantes para atualizar o PDI ou disparar e-mails. O Apache Kafka atua como o barramento de eventos (EDA), garantindo persistência durável e entrega ordenada com retenção em disco.

Segurança Centralizada (IAM)

Armazenar senhas e emitir tokens JWT diretamente na aplicação gera débito técnico de segurança. O Keycloak atua como Provedor de Identidade (IdP) compatível com padrões abertos OAuth 2.0 e OpenID Connect (OIDC), permitindo Single Sign-On (SSO) e validação criptográfica via JWKS.

FinOps & Shift-Left Cloud

Desenvolver diretamente na AWS real gera custos de infraestrutura, exige contas corporativas e pode provocar despesas acidentais. O LocalStack emula APIs da AWS no ambiente local, permitindo testar S3, SQS e Secrets Manager com fidelidade e custo zero de nuvem.

2. Explicação Conceitual & Funcionamento por Baixo dos Panos

Deep Dive Teórico

2.1 Apache Kafka em Modo KRaft (KIP-500): O Fim do ZooKeeper

Historicamente, o Kafka dependia de um sistema externo chamado Apache ZooKeeper. O ZooKeeper mantinha a árvore de nós do cluster, a lista de tópicos, o mapeamento de partições e elegia o nó líder. No entanto, essa arquitetura apresentava dois grandes gargalos:

  • Sincronização Dupla: O estado existia no ZooKeeper e precisava ser propagado via RPC para o controlador do Kafka, gerando latências de recuperação em clusters com milhões de partições.
  • Custo Operacional: Exigia subir e monitorar outro cluster distribuído com quórum ímpar (3 ou 5 nós), consumindo centenas de megabytes de RAM a mais.

Com a proposta KIP-500 (Kafka Improvement Proposal), o Kafka adotou o algoritmo de consenso Raft internamente, criando o KRaft (Kafka Raft metadata mode). Os próprios brokers Kafka armazenam os metadados em um tópico interno especial de log (`@metadata`). Em desenvolvimento local, um único container atua como broker e controller simultaneamente (`KAFKA_PROCESS_ROLES=broker,controller`), economizando mais de 400MB de RAM.

A Armadilha Clássica dos Listeners do Kafka no Docker

Uma das dúvidas mais comuns de desenvolvedores ao subir o Kafka em containers é: "Por que minha aplicação não conecta no Kafka, se a porta 9092 está aberta?". O Kafka tem um mecanismo de dois estágios de conexão:

  1. O cliente se conecta no endereço de Bootstrap inicial.
  2. O broker responde com a lista de Advertised Listeners (os endereços onde os líderes de partição realmente atendem).
  3. O cliente desconecta do bootstrap e abre nova conexão no endereço anunciado!

Se o Kafka anunciar `localhost:9092`, outro container dentro da rede Docker tentará conectar em `localhost` de si mesmo e falhará. Se anunciar `kafka:29092`, seu terminal na máquina host tentará resolver o nome DNS `kafka` e também falhará. Por isso, configuramos **múltiplos listeners dedicados**:

PLAINTEXT (29092) Rede interna Docker (`flowtask-kafka:29092`) para microsserviços.
PLAINTEXT_HOST (9092) Acesso via máquina host (`localhost:9092`) para CLIs e IDEs.
CONTROLLER (29093) Canal exclusivo de consenso Raft para eleição do cluster.

2.2 Keycloak 24+ com Quarkus Runtime e Importação Automática de Realm

O Keycloak moderno (versões 20+) foi completamente reescrito para utilizar o runtime **Quarkus** no lugar do antigo WildFly, proporcionando inicialização três vezes mais rápida e menor pegada de memória.

No FlowTask, utilizamos o recurso de Realm Import Declarativo. Em vez de exigir que o desenvolvedor clique manualmente na interface administrativa para criar o cliente OAuth2 e usuários de teste:

  • O arquivo canônico keycloak-config/flowtask-realm.json define o realm flowtask, o cliente flowtask-api e credenciais de teste.
  • O container sobe com o comando start-dev --import-realm.
  • Ao detectar o JSON na pasta /opt/keycloak/data/import/, o Keycloak migra as tabelas no PostgreSQL (flowtask_keycloak) e instancia o realm automaticamente.

2.3 LocalStack AWS Gateway: Simulação de Nuvem na Porta 4566

O LocalStack roda como um mock local hiper-eficiente das APIs da Amazon Web Services. Desde a versão 3.0, ele unificou todas as portas de serviços (que antigamente eram 4572 para S3, 4576 para SQS) em uma única porta Edge Service: 4566.

Quando o provider Terraform da AWS executa uma chamada como aws_s3_bucket ou aws_sqs_queue, ele envia a requisição HTTP assinada com credenciais dummy (`test`/`test`) para http://localhost:4566. O roteador interno do LocalStack inspeciona os cabeçalhos (`X-Amz-Target` ou o host da requisição) e despacha para o serviço emulado em memória.

4. Exemplos Práticos & Configurações HCL Explicadas

Código & Comandos
infra/terraform/modules/kafka/main.tf

Variáveis essenciais do KRaft configuradas no container Docker: 

resource "docker_container" "kafka" {
  name    = "flowtask-kafka"
  image   = docker_image.kafka.image_id
  restart = "unless-stopped"

  ports {
    internal = 9092
    external = var.host_port
  }

  networks_advanced {
    name    = var.network_id
    aliases = ["kafka", "flowtask-kafka"]
  }

  env = [
    "KAFKA_NODE_ID=1",
    "KAFKA_PROCESS_ROLES=broker,controller",
    "KAFKA_CONTROLLER_QUORUM_VOTERS=1@flowtask-kafka:29093",
    "KAFKA_LISTENERS=PLAINTEXT://0.0.0.0:29092,CONTROLLER://0.0.0.0:29093,PLAINTEXT_HOST://0.0.0.0:9092",
    "KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://flowtask-kafka:29092,PLAINTEXT_HOST://localhost:${var.host_port}",
    "KAFKA_LISTENER_SECURITY_PROTOCOL_MAP=CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT,PLAINTEXT_HOST:PLAINTEXT",
    "KAFKA_INTER_BROKER_LISTENER_NAME=PLAINTEXT",
    "KAFKA_CONTROLLER_LISTENER_NAMES=CONTROLLER",
    "CLUSTER_ID=${var.cluster_id}"
  ]
}
infra/terraform/modules/localstack/main.tf

Criação do container e provisionamento declarativo via provider AWS: 

# Bucket S3 no LocalStack
resource "aws_s3_bucket" "attachments" {
  bucket = "flowtask-attachments"
  depends_on = [docker_container.localstack]
}

# Fila SQS Dead Letter Queue
resource "aws_sqs_queue" "dlq" {
  name                      = "flowtask-deadletter-queue"
  message_retention_seconds = 86400
  depends_on = [docker_container.localstack]
}

# Segredo no AWS Secrets Manager
resource "aws_secretsmanager_secret" "app_secrets" {
  name        = "flowtask-secrets"
  description = "Credenciais e secrets centrais da aplicação FlowTask"
  depends_on = [docker_container.localstack]
}

5. Erros Comuns, Lições de Engenharia & Dicas para Entrevistas

Boas Práticas
1. Armadilha da Imagem 'latest' do LocalStack

Em builds recentes da tag localstack/localstack:latest, o runtime passou a exigir a variável LOCALSTACK_AUTH_TOKEN com código de saída 55 na ausência de licença. Solução de Engenharia: Fixar a versão na imagem estável da comunidade (localstack/localstack:3.8.0), garantindo previsibilidade e reprodutibilidade de CI/CD.

2. Caracteres Invisíveis CRLF (\r) em Ambientes Híbridos (Windows + WSL)

Editores no Windows utilizam CRLF (`\r\n`), enquanto o Linux e o analisador léxico do Terraform esperam LF (`\n`). A presença de um retorno de carro isolado no final do arquivo HCL gera o erro opaco: Error: Invalid character. This character is not used within the language. Solução: Normalizar os finais de linha com sed -i 's/\r//g' <arquivo> ou configurar .gitattributes com * text=auto eol=lf.

Como Defender Esta Arquitetura em Entrevistas Técnicas (ex: Itaú / Mercado Livre)

Quando o entrevistador perguntar sobre "Como você estruturou a infraestrutura local do seu projeto?", enfatize:

  • Paridade Dev/Prod: "Utilizamos Terraform com LocalStack para simular o mesmo contrato das APIs AWS (S3, SQS, Secrets Manager) que teremos em produção, eliminando o clássico 'na minha máquina funciona'."
  • Eficiência de Recursos: "Adotamos Kafka em modo KRaft eliminando o ZooKeeper, reduzindo o consumo de memória do ecossistema local em ~400MB de RAM."
  • Governança IAM Declarativa: "O Keycloak sobe com Realm automatizado via HCL e JSON, garantindo que qualquer desenvolvedor clone o repositório e tenha o ambiente OIDC funcional em segundos."

6. TL;DR — Pontos-Chave para Revisão Rápida

KRaft Standalone: Unifica broker e controller no nó 1 via consenso Raft, dispensando o ZooKeeper.
Mapeamento de Listeners: Porta 29092 para a bridge interna e 9092 para conexões do host.
Keycloak com Realm Import: Injeção do JSON do realm na pasta de importação do Quarkus conectada ao Postgres.
LocalStack Edge 4566: Ponto único de roteamento para serviços simulados de nuvem AWS (S3, SQS, Secrets).
