1. Arquitetura de Submódulos HCL Encapsulados

Em projetos de porte corporativo, colocar toda a infraestrutura em um único arquivo main.tf cria um antipadrão conhecido como "Monólito de Infraestrutura". Para garantir **alta coesão e baixo acoplamento**, cada serviço nesta fase foi encapsulado em um submódulo próprio dentro de infra/terraform/modules/<serviço>/.

A Tríade Canônica de um Módulo Terraform

variables.tf (Inputs)

Define os parâmetros que o módulo espera receber de quem o chamar (portas, nomes de banco, credenciais e IDs de rede). Atua como a lista de argumentos de uma função.

main.tf (Recursos)

Contém a declaração dos recursos reais (docker_image, docker_container, docker_volume). É onde a tecnologia é instanciada e configurada.

outputs.tf (Retornos)

Exporta informações computadas pelo container após a criação (IDs, URLs JDBC, URLs de acesso web HTTP e connection strings) para uso de outros módulos ou exibição no terminal.

O Princípio do Isolamento de Providers em Submódulos

No Terraform 0.13+, cada submódulo é um namespace isolado. Se o submódulo usa recursos como docker_container sem declarar seu provider, o Terraform tenta buscar por padrão o inexistente hashicorp/docker. Por isso, todo submódulo deve conter explicitamente em seu topo: 

terraform {
  required_providers {
    docker = {
      source = "kreuzwerker/docker"
    }
  }
}

3. Detalhamento Técnico dos 5 Módulos Implementados

2.1 PostgreSQL 15 Alpine (Banco Relacional Core) Porta 5432

O PostgreSQL atua como o banco de dados relacional primário do ecossistema FlowTask, armazenando tabelas de usuários, perfis, tarefas e também a base de dados dedicada do servidor de autenticação Keycloak.

💡 A Técnica de Inicialização de Múltiplos Bancos (`upload`):

A imagem oficial do Postgres só cria nativamente um banco via variável POSTGRES_DB=flowtask. Para criar o segundo banco exigido pelo Keycloak (flowtask_keycloak), utilizamos o gancho nativo do entrypoint: qualquer arquivo SQL dentro de /docker-entrypoint-initdb.d/ é executado na primeira inicialização. 

upload {
  content = "CREATE DATABASE flowtask_keycloak;\n"
  file    = "/docker-entrypoint-initdb.d/init-keycloak.sql"
}
2.2 pgAdmin 4 (Interface Visual Web para PostgreSQL) Porta 5050 (HTTP)

Interface visual completa para gerenciar tabelas, rodar queries SQL e inspecionar índices sem precisar instalar softwares pesados na máquina do desenvolvedor.

Mapeamento de Portas (80 -> 5050)

Internamente no container, o servidor web roda na porta HTTP padrão 80. O Terraform mapeia para a porta externa 5050 para não disputar portas do host.

Variáveis de Bootstrap

PGADMIN_DEFAULT_EMAIL e PGADMIN_DEFAULT_PASSWORD definem a conta administrativa inicial criada no boot.

2.3 MongoDB 7.0 (Banco NoSQL Documental) Porta 27017

Banco NoSQL orientado a documentos JSON/BSON. No FlowTask, é utilizado para armazenar dados dinâmicos, auditorias e logs de transações sem esquema rígido (schemaless).

🍃 Parâmetros Chave:
  • Pasta de persistência do motor WiredTiger: /data/db.
  • Variáveis MONGO_INITDB_ROOT_USERNAME e MONGO_INITDB_ROOT_PASSWORD habilitam autenticação estrita no banco admin.
  • Comando de auditoria rápida: mongosh -u root -p root --eval "db.adminCommand({ping: 1})" retornando { ok: 1 }.
2.4 Mongo Express (Interface Visual Web para MongoDB) Porta 8081 (HTTP)

Aplicação web leve em Node.js/Express para visualização e edição de documentos BSON direto no navegador.

⚙️ Variável Crucial para Conexão em Rede Privada:

ME_CONFIG_MONGODB_SERVER=mongo faz o Mongo Express resolver o IP do container MongoDB via DNS interno da rede bridge. A flag ME_CONFIG_BASICAUTH=false desativa o diálogo HTTP de autenticação básica em desenvolvimento, permitindo acesso imediato ao painel.

2.5 Redis 7 Alpine (Cache In-Memory & Estrutura Chave-Valor) Porta 6379

Banco de dados chave-valor residente em memória RAM, com tempos de resposta sub-milissegundo (< 1ms). Utilizado para caching de sessões, contadores e invalidação rápida.

⚡ O que é o modo AOF (`--appendonly yes`)?

O Redis possui duas estratégias de persistência: RDB (Snapshots pontuais) e AOF (Append Only File). Com command = ["redis-server", "--appendonly", "yes"], cada operação de escrita é gravada sequencialmente em disco na pasta /data. Se o container reiniciar, nenhum dado de cache é perdido!

4. O Dilema de Sistemas de Arquivos: NTFS do Windows vs. POSIX ext4 do Linux

Um dos momentos mais valiosos de aprendizado prático desta fase ocorreu quando o container do PostgreSQL entrou em loop de reinicialização (Restarting) com o erro:

chmod: /var/lib/postgresql/data: Operation not permitted
initdb: error: could not change permissions of directory "/var/lib/postgresql/data": Operation not permitted
Por que o Bind Mount Falhou no Windows?

O sistema de arquivos NTFS do Windows (montado no WSL via driver drvfs em /mnt/c/) não implementa permissões POSIX nativas de propriedade e controle de acesso Unix. Como o PostgreSQL exige obrigatoriamente permissão estrita 0700 (para evitar que outros usuários do SO leiam arquivos do banco), o script initdb aborta imediatamente.

Por que o Docker Named Volume é a Solução?

O recurso docker_volume aloca espaço dentro da máquina virtual Linux interna (ext4) do Docker Desktop. Como o ext4 é um sistema de arquivos Linux nativo, comandos como chmod 0700 e chown postgres:postgres funcionam instantaneamente com 100% de conformidade de segurança!

5. O Caderno de Erros da Fase 2 (Diagnóstico & Solução Rápida)

1. Executar terraform apply dentro da pasta do submódulo Erro de Escopo

Sintoma: O Terraform faz perguntas interativas no terminal sobre variáveis sem default (ex: var.network_id: Enter a value:). Ao digitar yes, o container falha com network yes not found!

Solução: Submódulos nunca devem ser executados isoladamente. Comandos como terraform plan/apply são executados exclusivamente na raiz (infra/terraform/), que passa as variáveis certas aos módulos filhos.

2. Aspas em referências de atributos HCL Sintaxe HCL

Incorreto: image = "docker_image.postgres.image_id" (o Terraform trata como texto literal).
Correto: image = docker_image.postgres.image_id (sem aspas, avaliado dinamicamente como ponteiro para o recurso).

3. Reference to undeclared resource docker_volume Validação Estática

Causa: Usar docker_volume.redis_data.name dentro do container sem ter criado o bloco resource "docker_volume" "redis_data" no mesmo arquivo.
Dica: Sempre declare o recurso antes de tentar ler seus atributos.

4. Hífen vs. Underline (`flowtask-mongo` vs. `flowtask_mongo`) Docker Daemon

O Docker Daemon é estritamente literal. Se o container foi nomeado com flowtask_mongo, qualquer comando com flowtask-mongo retornará No such container. Em times de engenharia, padronize todos os nomes usando kebab-case (flowtask-servico).

6. TL;DR — Resumo da Fase 2 para Revisão Rápida

  • Tríade HCL: Todo submódulo possui variables.tf (inputs), main.tf (recursos) e outputs.tf (retornos).
  • Docker Named Volumes no Windows: Para evitar erros de chmod 0700 Operation not permitted do PostgreSQL no NTFS, utiliza-se docker_volume gerenciado na partição ext4 do Docker Desktop.
  • Initdb Automatizado: O bloco upload do Terraform injeta scripts em /docker-entrypoint-initdb.d/, criando o banco auxiliar flowtask_keycloak na primeira subida.
  • Interfaces Web: pgAdmin na porta 5050 e Mongo Express na porta 8081 conectam-se aos respectivos bancos via DNS interno (postgres:5432 e mongo:27017).
  • Redis AOF: A flag --appendonly yes ativa durabilidade transacional em disco na pasta /data.
