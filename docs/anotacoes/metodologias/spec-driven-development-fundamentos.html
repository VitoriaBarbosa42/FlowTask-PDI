Spec-Driven Development (SDD) — Fundamentos

Resumo Rápido

O Spec-Driven Development é uma metodologia onde a especificação técnica é a fonte única da verdade e o código é tratado como um artefato derivado. Em fluxos assistidos por Agentes de IA (Claude Code, Cursor, Copilot), o SDD substitui o "codar no chute" por um ciclo previsível de Spec → Plano → Código → Verificação, reduzindo drasticamente custos de tokens, retrabalho e bugs em produção.

1. Por Que Isso Importa? (Contexto & Aplicação Prática)

Com o avanço dos modelos de IA no desenvolvimento de software, a velocidade de geração de código aumentou exponencialmente. No entanto, surgiu um novo gargalo crítico: a imprevisibilidade.

❌ O Problema: Codar no Chute (Vibe Coding)

Ao digitar prompts vagos como "Faz um sistema de login", a IA adivinha (alucina) decisões arquiteturais críticas (JWT vs Sessão, BCrypt, banco, erros 401). Após minutos e centenas de tokens gerando 400 linhas de código, o código não serve e exige refatoração cara.

✅ A Solução: Spec-Driven Development

A especificação técnica delimita o escopo (o que está dentro e fora), regras invariantes e contratos de dados. O agente implementa com precisão cirúrgica de primeira, sem ambiguidades.

Quando Usar:
  • Desenvolvimento com Agentes de IA / Harness.
  • Features críticas com regras de negócio e APIs.
  • Equipes que buscam previsibilidade e contratos claros.
Quando NÃO Usar:
  • Scripts one-off descartáveis.
  • Correções de uma única linha ou typos pontuais.

2. Explicação Conceitual & A Regra de Ouro

"Se o código é o COMO, a SPEC é o O QUÊ e o PORQUÊ."

Se você decidir reescrever uma aplicação inteira de Python para Go ou de Node.js para Java, todo o "COMO" (implementação) muda. No entanto, nenhuma linha da SPEC deveria mudar, pois as regras de negócio e requisitos são agnósticos a tecnologia.

Documentação Morta vs. Spec Executável (Viva)

Característica Documentação Morta (Tradicional) Spec Executável (SDD)
Momento Escrita após o código (post-mortem). Escrita ANTES de gerar plano ou código.
Consumo Raramente lida; serve para prestar contas. Input direto para o Agente de IA e equipe.
Evolução Fica desatualizada no 1º commit sem ninguém notar. Desatualizar quebra o ciclo e o erro aparece logo.

4. Exemplo Prático: Comparativo de Entrada

❌ Pedido no Chute (Vago) 
"Crie um endpoint de login para
minha aplicação."

A IA é forçada a adivinhar campos, tokens, criptografia, tabela de usuários e tratamento de erros.

✅ Spec Executável Estruturada 
# Spec: Login JWT
- Endpoint: POST /api/v1/auth/login
- In-Scope: email + password, BCrypt,
  emissão de JWT (exp: 2h).
- Out-of-Scope: OAuth2, Social Login.
- Critérios: 200 OK com token,
  401 em credenciais inválidas.

Zero adivinhação. A IA entrega o código exato alinhado com a infraestrutura no primeiro ciclo.

5. Objeções Clássicas & Dicas para Entrevistas

Objeção 1: "Escrever Spec é muito lento." Levar 5 minutos escrevendo a Spec economiza horas corrigindo alucinações e depurando código incorreto. O tempo total até a entrega funcional é menor.
Objeção 2: "A IA já é inteligente e adivinha o que eu quero." Por ser probabilística, a IA preenche lacunas com soluções genéricas que frequentemente colidem com os padrões da sua arquitetura corporativa.
Dica de Ouro para Entrevistas Técnicas:

"Em entrevistas de System Design e Live Coding com IA, enfatize que você adota uma abordagem Spec-First: define escopos claros (In/Out-of-Scope), invariantes e critérios de aceite antes de codar. Isso demonstra senioridade, liderança técnica e previsibilidade de engenharia."

6. TL;DR (Pontos-Chave para Revisão Rápida)

  • A Spec é a Fonte da Verdade: O código é derivado e descartável.
  • Agnosticismo Tecnológico: Mudar de Python para Go altera o COMO, nunca o O QUÊ.
  • Economia Real: Erros na Spec custam centavos; erros em produção custam a reputação do produto.
  • Ciclo SDD: Spec → Plan → Code → Verify.
