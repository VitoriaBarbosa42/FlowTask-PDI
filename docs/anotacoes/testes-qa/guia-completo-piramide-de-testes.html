A Arte dos Testes Automatizados: Da Teoria à Prática no Código

Como arquitetar, organizar e codificar testes unitários isolados com Mockito, testes de integração reais contra containers descartáveis via Testcontainers e testes de API com MockMvc, garantindo que nenhum bug chegue a produção.

A Grande Virada de Chave: Testar manualmente com comandos de terminal (como curl ou docker exec) é útil durante o desenvolvimento de infraestrutura, mas o que protege o código em produção são baterias automatizadas que rodam em segundos a cada git push. Aqui você aprenderá como construir essa rede de segurança do zero.

1. Por Que Testes Automatizados Importam? (O Custo da Falha)

Fundamento de Engenharia
Proteção Contra Regressão

Regressão acontece quando uma alteração nova quebra uma regra antiga que já funcionava. Uma suíte sólida de testes roda antes de cada commit e avisa na hora: "O que você alterou quebrou a regra de conclusão de tarefas da Sprint 2".

Coragem para Refatorar

Desenvolvedores têm medo de limpar código feio quando não existem testes, com medo de introduzir bugs ocultos. Com testes automatizados, você refatora livremente com a certeza matemática de que o comportamento externo permanece idêntico.

Documentação Viva do Sistema

Comentários e wikis ficam desatualizados com o tempo. Testes nunca mentem: eles descrevem exatamente quais são as entradas aceitas, as regras de negócio e como a aplicação reage a erros em código compilável e executável.

1. Nível Unitário ~70%

Testa uma única classe (ex: um Service ou Domain Model) isolando todas as suas dependências externas (como Repositórios, APIs ou Filas) usando Mocks.

⚡ Velocidade: 1 a 20 ms
🚫 Spring Boot: NÃO carrega o contexto
🧰 Ferramentas: JUnit 5, Mockito, AssertJ
2. Nível de Integração ~20%

Testa se duas ou mais partes conversam de verdade. No lugar de usar banco falso H2 em memória, usa Testcontainers para subir PostgreSQL 15 ou Kafka real em Docker temporário.

⚡ Velocidade: 500 ms a 3s
🌱 Spring Boot: Carrega fatias (`@DataJpaTest`)
🧰 Ferramentas: Spring Test, Testcontainers
3. Nível E2E / API ~10%

Simula um cliente real (Postman, Mobile, Frontend) disparando requisições HTTP REST com JSON e verificando códigos de status, headers, body e efeitos colaterais no banco.

⚡ Velocidade: 1s a 5s
🌐 Spring Boot: Servidor HTTP ativo
🧰 Ferramentas: MockMvc, RestAssured

3. O Padrão Universal AAA (Arrange, Act, Assert)

Estrutura Canônica de um Teste Limpo

Todo bom teste automatizado, seja unitário ou de integração, deve ser lido como uma história linear em 3 blocos bem definidos:

1. Arrange (Preparar / Dado que)

Configura o cenário inicial. Cria entidades, instancia objetos com dados válidos e instrui os mocks sobre como devem responder:

when(repo.findById(1L)).thenReturn(tarefa);
2. Act (Agir / Quando)

Executa a operação ou método alvo sendo testado. Deve ser apenas uma linha de código:

Tarefa resultado = service.concluir(1L);
3. Assert (Verificar / Então)

Valida o resultado final e garante que os efeitos colaterais esperados aconteceram com AssertJ e verify:

assertThat(resultado.getStatus()).isEqualTo(CONCLUIDO);

4. Código Hands-on: Como Implementar no FlowTask

Java 25 & Spring Boot
Exemplo 1: Teste Unitário com Mockito & AssertJ (Sem Spring) Tempo: ~15ms

Usamos @ExtendWith(MockitoExtension.class) para testar a lógica pura sem pagar o custo de inicializar o container do Spring Boot: 

package br.com.flowtask.service;

import br.com.flowtask.domain.Tarefa;
import br.com.flowtask.domain.Status;
import br.com.flowtask.exception.TarefaNaoEncontradaException;
import br.com.flowtask.repository.TarefaRepository;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import java.util.Optional;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.Mockito.*;

@ExtendWith(MockitoExtension.class) // Inicialização pura, sem banco e sem Spring!
class ConcluirTarefaServiceTest {

    @Mock
    private TarefaRepository tarefaRepository;

    @Mock
    private KafkaEventProducer kafkaProducer;

    @InjectMocks
    private ConcluirTarefaService service;

    @Test
    @DisplayName("Deve concluir tarefa com sucesso e emitir evento assíncrono para o Kafka")
    void deveConcluirTarefaComSucesso() {
        // 1. Arrange (Preparação)
        Tarefa tarefaExistente = new Tarefa(1L, "Modelar Banco", Status.FAZENDO);
        when(tarefaRepository.findById(1L)).thenReturn(Optional.of(tarefaExistente));
        when(tarefaRepository.save(any(Tarefa.class))).thenAnswer(invocation -> invocation.getArgument(0));

        // 2. Act (Ação)
        Tarefa resultado = service.concluir(1L);

        // 3. Assert (Validação com AssertJ)
        assertThat(resultado).isNotNull();
        assertThat(resultado.getStatus()).isEqualTo(Status.CONCLUIDO);

        // Verifica que o repository salvou e o Kafka recebeu o evento exatamente 1 vez
        verify(tarefaRepository, times(1)).save(tarefaExistente);
        verify(kafkaProducer, times(1)).publicarTarefaConcluida(any());
    }

    @Test
    @DisplayName("Deve lançar TarefaNaoEncontradaException quando ID não existir")
    void deveLancarExcecaoQuandoIdNaoExiste() {
        // Arrange
        when(tarefaRepository.findById(999L)).thenReturn(Optional.empty());

        // Act & Assert
        assertThatThrownBy(() -> service.concluir(999L))
            .isInstanceOf(TarefaNaoEncontradaException.class)
            .hasMessage("Tarefa com ID 999 não encontrada");

        // Garante que nenhuma mensagem foi enviada ao Kafka em caso de erro!
        verifyNoInteractions(kafkaProducer);
    }
}
Exemplo 2: Teste de Integração com Testcontainers (PostgreSQL Real) Tempo: ~1.8s

O código Java comanda o Docker para provisionar um PostgreSQL 15 descartável antes dos testes e injeta a URL dinâmica no Spring Data JPA: 

package br.com.flowtask.repository;

import br.com.flowtask.domain.Tarefa;
import br.com.flowtask.domain.Status;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.jdbc.AutoConfigureTestDatabase;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

import java.util.Optional;

import static org.assertj.core.api.Assertions.assertThat;

@DataJpaTest // Sobe apenas os repositórios JPA (muito mais rápido que @SpringBootTest inteiro)
@Testcontainers // Habilita o ciclo de vida do Docker gerenciado pelo JUnit
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE) // Desativa o H2 falso!
class TarefaRepositoryIT {

    // Sobe o container oficial do Postgres idêntico ao provisionado pelo Terraform
    @Container
    static PostgreSQLContainer postgres = new PostgreSQLContainer<>("postgres:15-alpine")
            .withDatabaseName("flowtask_test")
            .withUsername("test")
            .withPassword("test");

    // Injeta a porta aleatória e segura gerada pelo Docker nas propriedades do Spring
    @DynamicPropertySource
    static void configureDatasource(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired
    private TarefaRepository repository;

    @Test
    @DisplayName("Deve persistir tarefa no PostgreSQL 15 real e recuperar por ID")
    void deveSalvarEBuscarNoBancoReal() {
        // Arrange
        Tarefa novaTarefa = new Tarefa(null, "Aprender Testcontainers", Status.A_FAZER);

        // Act
        Tarefa salva = repository.save(novaTarefa);

        // Assert
        Optional recuperada = repository.findById(salva.getId());
        assertThat(recuperada).isPresent();
        assertThat(recuperada.get().getTitulo()).isEqualTo("Aprender Testcontainers");
        assertThat(recuperada.get().getId()).isNotNull();
    }
}
Exemplo 3: Teste de API com MockMvc (Validação de Contrato HTTP) Tempo: ~350ms

Testa a camada REST (rotas, validação de payload, headers e conversão JSON) isolando a regra de negócio via mock: 

package br.com.flowtask.controller;

import br.com.flowtask.domain.Tarefa;
import br.com.flowtask.domain.Status;
import br.com.flowtask.service.ConcluirTarefaService;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
import org.springframework.boot.test.mock.mockito.MockBean;
import org.springframework.http.MediaType;
import org.springframework.test.web.servlet.MockMvc;

import static org.mockito.Mockito.when;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.patch;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@WebMvcTest(TarefaController.class) // Fatiamento: sobe apenas a camada Web MVC
class TarefaControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockBean
    private ConcluirTarefaService service;

    @Test
    @DisplayName("PATCH /api/tarefas/{id}/concluir deve retornar 200 OK com JSON esperado")
    void deveRetornarStatus200AoConcluirTarefa() throws Exception {
        Tarefa tarefaConcluida = new Tarefa(10L, "Deploy Terraform", Status.CONCLUIDO);
        when(service.concluir(10L)).thenReturn(tarefaConcluida);

        mockMvc.perform(patch("/api/tarefas/10/concluir")
                .contentType(MediaType.APPLICATION_JSON))
                .andExpect(status().isOk())
                .andExpect(content().contentType(MediaType.APPLICATION_JSON))
                .andExpect(jsonPath("$.id").value(10))
                .andExpect(jsonPath("$.status").value("CONCLUIDO"))
                .andExpect(jsonPath("$.titulo").value("Deploy Terraform"));
    }
}

Sufixo *Test.java (Surefire Plugin)

Executado no comando padrão ./mvnw test. Roda todos os testes unitários em poucos segundos. Se qualquer um falhar, o build quebra imediatamente.

Sufixo *IT.java (Failsafe Plugin)

Executado no comando ./mvnw verify. Roda os testes de integração pesados (Testcontainers) após o empacotamento do JAR.

6. Erros Clássicos de Iniciantes & Dicas para Entrevistas

Armadilhas & Anti-Patterns
1. Colocar @SpringBootTest em Tudo

Anotar @SpringBootTest num teste unitário faz o Spring subir DataSource, JPA, Security e beans desnecessários, transformando uma suíte que deveria rodar em 2 segundos num processo lento de 3 minutos. Regra: Se o teste é unitário de lógica de negócio, use apenas @ExtendWith(MockitoExtension.class).

2. Usar Lógica Dentro do Teste (if, for, while)

Testes não devem conter estruturas condicionais (if) ou laços (for). Se o teste possui lógica própria, ele próprio pode conter bugs que mascaram falhas! O teste deve ser estritamente linear e declarativo.

3. Confiar Cegamente no Banco H2 em Memória

O H2 não suporta índices JSONB do PostgreSQL, funções específicas de data ou concorrência real. Um teste que passa no H2 frequentemente explode em produção. Testcontainers é o padrão atual da indústria para paridade 100% fiel com o banco real.

Como Explicar Sua Estratégia de Testes em Entrevistas

Em entrevistas técnicas, quando te perguntarem "Como você garante a qualidade do seu código?", responda com autoridade:

  • "Adoto a Pirâmide de Testes: foco a maior parte do esforço na base com testes unitários rápidos e determinísticos com JUnit 5 e Mockito para cobrir regras de negócio."
  • "Para validação de persistência e eventos, uso Testcontainers. Isso nos dá a segurança de rodar testes contra o PostgreSQL 15 e Kafka reais em Docker descartável, eliminando a discrepância do H2."
  • "Organizo os testes no padrão AAA (Arrange, Act, Assert) e integro a execução na pipeline de CI/CD para que nenhum PR seja aceito sem testes passando."

7. TL;DR — Resumo dos Pontos-Chave

Unitário vs Integração: Unitário testa classes isoladas em ms sem Spring; Integração valida conversa real com Docker Testcontainers.
Estrutura AAA: Todo teste deve ter 3 partes explícitas: Preparar dados (Arrange), Agir (Act) e Validar (Assert).
AssertJ é Melhor que assertEquals: A sintaxe fluente assertThat(x).isEqualTo(y) é legível e gera mensagens de erro muito mais claras.
Paridade Real com Testcontainers: Testar o PostgreSQL e o Kafka reais em containers temporários garante zero surpresas em produção.
